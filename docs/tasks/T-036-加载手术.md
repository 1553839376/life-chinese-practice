# T-036 · 加载手术：语音包挪到末尾，加载页不再自己跑掉

- **日期**：2026-11-05
- **版本**：v41 / v42 → **v43 已整体撤回**
- **状态**：❌ **已撤回**（2026-11-05，用户实测发现字卡声音变成浏览器自带语音，`build/` 退回 `efc53f9`）

## 一、起因

老师问「现在是继续加新游戏，还是优化现有动效，这些会不会增加很多网页负担，是否需要先优化一轮加载速度」。
先算体积账，发现结论和直觉相反：**动效完全不是负担，游戏代码只占 0.3%**。

| 组成 | 体积 | 占比 |
|---|---|---|
| 语音包（1695 条，base64） | 12.90 MB | **87.6%** |
| 图示（111 张 SVG） | 0.75 MB | 5.1% |
| 笔顺数据（561 字） | 0.54 MB | 3.7% |
| 全部 JS + CSS | 约 0.55 MB | 3.6% |
| **其中游戏代码 `p7.js`** | **0.05 MB** | **0.3%** |

动效侧也盘过了：29 条 `@keyframes` 里 **25 条只用 `transform`**，3 条用 `box-shadow`（喇叭脉冲，屏幕上同时只有 1~2 个元素），
**没有一条动画用 `filter` / `blur`**，同时动画的元素是个位数。所以加动效对体积（<2 KB）和 GPU 都几乎零成本。

然后查加载链路，发现真问题。

## 二、真问题：加载页在「装死」

拼接顺序原来是：

```
样式 → 结构 → 【12.90 MB 语音包】 → 音效 → 图库 → 字库 → 数据层 → … → 游戏
```

浏览器必须读完一个 `<script>` 元素才能执行它（`type="application/json"` 也一样——它是 data block，解析器要读到
`</script>` 才能往下走）。所以 12.9 MB 音频把后面 2.5 MB 的脚本全堵住了。

而加载页写死了：

```css
.boot-mask{ animation:bootFade .45s ease 2.4s forwards }
```

**2.4 秒无条件淡出，不管页面准备好没有。** 于是教室 10 Mbps 下的真实一幕是：

1. 0～2.4 秒：米色遮罩 + 绿圈 +「认字乐园 / 正在准备字卡和声音…」——**这一段体验是好的**；
2. 2.4～2.85 秒：遮罩自己淡出，露出 `#scrPick`（唯一没有 `hidden` 的屏）：导航条 +「班级练习 / 点一下自己的照片，开始今天的练习」+ **一片空白的照片格**；
3. 2.85～8 秒：就停在这一屏。**它写着「点照片」，而一张照片都没有**——孩子会去戳，戳不动；
4. 约 8 秒：脚本终于到，`boot()` 跑完，照片和字格一次性出现。

第 3 段比一直转圈更糟：它假装加载完了。

## 三、改了什么

| 位置 | 改动 |
|---|---|
| `build/build_html.py` | 语音包从「结构之后、TAIL 之前」移到 **主脚本关闭之后、`</body>` 之前**（`p_close.txt` 按 `</body>` 切开插进去）；紧跟一行 `<script>if (window.voicePackWarm) voicePackWarm();</script>` |
| `build/p1.html` | `.boot-mask` 去掉 `animation:bootFade .45s ease 2.4s forwards`，改为 `.boot-mask.out{animation:bootFade .45s ease forwards}`（由 JS 触发）；新增 `.boot-slow` 纯 CSS 12 秒延时淡入 |
| `build/p2.html` | 加载文案「正在准备字卡和声音…」→「正在准备字卡…」；加 `<span class="boot-slow">网络有点慢，再等几秒…</span>` |
| `build/p6.js` | `boot()` 末尾撤遮罩从 `removeChild` 直接删，改成先 `classList.add('out')` 走 0.45 秒淡出、460ms 后再摘 DOM |
| `harness/run_gate.py` | G1 新增 4 条护栏 |
| `harness/manifest.json` | 登记 `voicePackLoad` / `voicePackWarm` / `bootMask` |

`vaB64` / `vaPlay` 的分支没动：音频没到时取不到 base64，`vaPlay` 会走 `saySystem` 用**系统语音**顶上，
所以「点喇叭完全没声」这种最坏情况不会发生——只是音色会短暂变成系统 TTS。

## 四、验收

**结构**（构建后实测）：

- 语音块位置：产物 15,443,352 字节中位于第 1,612,179 字符处，**其后只有一个触发脚本**，没有别的普通 `<script>`；
- 首屏需要下载的字节：**15.44 MB → 1.83 MB（-88%）**（语音块落在第 1,822,394 字符处）。

**功能**（jsdom 探针）：

```
boot 当刻  → VOICE_PACK=null | bootMask=在 | 字格 0 个
120ms 后   → VOICE_PACK=1695 条 | bootMask=在 | 字格 700 个
1000ms 后  → VOICE_PACK=1695 条 | bootMask=已移除
vaB64 取一条 → 6456 字符 base64（声音真能取到）
```

「惰性」这次是真生效了：boot 当刻语音包还是 `null`，是末尾那行脚本在音频到达后才 parse 的。

**A/B 计时**（jsdom，同一台机器，各跑 2 次取中位数）：

| 顺序 | 字格可用 |
|---|---|
| 旧（语音在中间） | 6509 ms（各次 5048 / 6509） |
| 新（语音在末尾） | 5067 ms（各次 4972 / 5067） |

省 1.44 秒（22%）。注意 jsdom 不模拟网络，这 1.44 秒是**纯解析器等待**；真实网络下的收益要大得多
（教室 10 Mbps 约 8 秒 → 约 1.5 秒），因为差别在「什么时候能开始执行脚本」。

**门禁**：158 → **162 项**，测试 859 项不变，全绿。

新增 4 条：

1. 语音包排在所有脚本之后；
2. 语音包下完会自动解析（末尾触发脚本在位）；
3. 加载页不再自己定时淡出（旧规则必须消失、`.out` 规则与 `classList.add('out')` 都在）；
4. 慢网络提示是纯 CSS 12 秒，不依赖 JS。

**截图**：`build/shot_v41_boot.png`（正常加载页）、`build/shot_v41_slow.png`（12 秒后的慢提示）。

## 五、踩过的坑

- **写护栏时把末尾那行触发脚本当成了「普通脚本」**，导致「语音块必须在最后」这条自己判红。
  改成先把触发脚本从待检查文本里剔掉再取 `max(script 位置)`。
- **`.boot-slow` 一开始看着像宋体**，怀疑字体继承断了。用 `--dump-dom` + `getComputedStyle` 打出来比对，
  三行的 `font-family` 完全一致（同一套系统栈），差异只是 14px 与 22px 加粗的观感。判「字体不对」先量声明，别凭眼睛。
  颜色从 `#9A8F76` 调到 `#8B7F66` 提升对比度。
- **第一版把语音块追加到 `</html>` 之后**（`p_close.txt` 结尾就是 `</body></html>`），浏览器容错能跑但不合规；
  改成按 `</body>` 切开插在中间。
- **护栏量错了位置**：`p8.js` 注释里也有 `<script type="application/json" id="voicePack">` 这串字，
  `find` 命中的是注释（1.6 MB 处），真实块在 1.83 MB 处 —— 要用 `rfind`。第一条「首屏 1.66 MB」是错的。
- **headless 截图必须用绝对 Windows 路径**，`--screenshot="相对名.png"` 会报「拒绝访问 (0x5)」。
- 加载页文案必须跟着改口：现在遮罩撤掉时声音确实还没到，继续写「正在准备字卡和声音」就是在撒谎。

## 六、回滚方式

改的是 4 个构建分片 + 1 个构建脚本，`git revert` 或 `git checkout <v40 的 commit> -- build/` 即可回到旧顺序。
线上 v40 未受影响，随时可以重发 v40。

## 七、下一步（未做）

- 语音包再往下还能拆：把「首屏必用」的音（指令句 22 条）与「按字」的音分开，但 `JSON.parse` 12.9 MB 在旧平板上
  仍要 0.5~1.5 秒，真要再快得改成分片懒加载——那会破坏「单文件离线可用」这条铁律，暂不做。

  这是平台行为，改不了。

## 八、撤回（2026-11-05，当天）

老师反馈原话：「不对呀，这样我打开听的字卡的声音变成浏览器自带的了，不是我想要的，先退回」。

**这不是玄学，是这条手术的结构性代价：**

| | v40（撤回后） | v42（手术版） |
|---|---|---|
| 语音 JSON 位置 | 109,558 字节处，**所有脚本之前** | `</body>` 之前，第 1.85 MB 起、长 12.9 MB |
| `boot()` 何时跑 | `p6.js` 末行 `else boot();`，**同步执行**（不是 DOMContentLoaded） | 同左 |
| `boot()` 跑时语音到没到 | 到了（字节在脚本之前） | **没到** |
| `getElementById('voicePack')` | 找到 | `null` |
| `vaB64()` 返回 | base64 | `''` |
| 听到的声音 | 豆包知性女声 | `saySystem()` → **浏览器自带语音** |

`boot()` 是同步的这一点是关键：整个应用从第 2.4 MB 起就活了，而语音要到第 14.5 MB 才落地。这段窗口就是「首屏能点、但一点就是系统音」的窗口。老师点得快，几乎必踩。

**结论**：加载手术本质是「拿声音换速度」。对课堂来说声音是第一位的，速度只能从别处省。**语音必须和首屏同时到。**

**撤回动作**：
1. `git checkout efc53f9 -- build/ harness/`（v40 那次发布的源码与门禁）
2. `APP_VER` / 角标改 `v43`（线上版本号不往回走）
3. 重新构建 → 门禁 158 项 0 红 / 859 项 0 失败 → 发布
4. 自动 `cache`（ETag 304）这条路走不通：平台不给设 `Cache-Control`，每次发版 URL 目录都变。

**以后要提速，只能走这几条（都还没做）**：语音按「首屏必用的指令句 22 条 / 按字的音」拆两段，前面那几百 KB 先到，剩下的再惰性加载——但要保住「单文件离线可用」，就得接受首屏仍有 1~2 MB；或者干脆认了，教学场景下 8 秒加载可以被接受，声音错了不行。
